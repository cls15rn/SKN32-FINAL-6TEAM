# Google Routes 교체 검토 — 2026-09-10

**결정: 현재 요구사항에 대한 전면 교체는 보류한다.** 대중교통 후보 조회는 유망하지만 독립 도보·차량 경로와 이력 저장·외부 에이전트 전달 조건이 해결되지 않았다. 이동수단 범위는 줄이지 않는다. 기존 제공자 설정·코어 계약·규칙은 바꾸지 않았다.

공개 문서에 명시된 조건과 프로젝트 적용에 대한 해석을 구분했다. 한국 결제계정에 적용되는 일반 약관 기준이며, 실제 결제계정 주소·별도 계약은 확인하지 않았다. 관광객 국적만으로 EEA 계약 적용을 결정하지 않는다. 업체 문의는 보내지 않았다.

## 2. 구현 전에 해결할 기능 차이

1. **요청 출발 시각 + duration만으로 도착을 계산하면 틀릴 수 있다.** 심야 철도·공항 T2 사례에서 요청 시점부터 마지막 도착까지의 시간이 route duration보다 길었다. API가 제시한 승하차 시각을 이용하고, 최초 승차 대기와 마지막 접근 도보를 구분해야 한다. 기존 카카오 규칙의 배차 절반 대기를 구글 총시간에 일괄 가산하는 것도 금지할 구현 패턴이다.
2. **철도 선호는 강제 제외 조건이 아니다.** 심야 RAIL 요청에도 버스 후보가 반환됐다. 운행 중단 노선·금지 수단은 반환된 후보에서 별도 검사해야 한다. 필터링 후 후보가 없다고 전체 대안이 없다고 증명되는 것도 아니다. [대중교통 요청 설명](https://developers.google.com/maps/documentation/routes/transit-route)
3. **도보 필드 생략을 구분해야 한다.** T2·주말 사례 일부 WALK 단계는 거리 필드가 생략됐지만 시간은 있고 시작·끝 좌표가 같았다. 0 기본값 생략일 가능성이 있으므로 곧바로 장애라 단정하지 않는다. 반대로 실제 실내 보행거리가 0이라는 증거도 아니다. [기본값 생략](https://developers.google.com/maps/documentation/routes/choose_fields), [단계별 필드가 없을 수 있다는 명세](https://developers.google.com/maps/documentation/routes/reference/rest/v2/TopLevel/computeRoutes#RouteLegStep)
4. **독립 도보·차량 소스가 필요하다.** 테스트 3건 모두 빈 결과이며 [한국 지원표](https://developers.google.com/maps/coverage)도 확인했다. 이를 실제 이동 불가로 해석해서는 안 된다. 택시 배차·실제 요금도 이번 테스트에서 검증하지 않았다.
5. **영어 완결성을 보장하지 않는다.** 영어 요청에서도 대중교통 텍스트에 비ASCII 내용이 남았다. 이전 응답에서 한글 노선·방향명도 관찰했다. 이름 표시와 설명 방식을 별도로 검토해야 한다.
6. 운영사 시간표 대조, 실시간 장애 반영, 접근성, 공항 출입구 보행, 도보 상한 정확도는 미검증이다. API 내부 시각 순서는 검사했지만 현장 운행 사실의 검증은 아니다.

## 4. 우리 구조에 적용한 판단 — 별도 해석

- **자체 판정 이력:** 사용자 입력·자체 규칙·독립 공공자료와 Google 유래 값을 분리해야 한다. Google 소요에서 만든 지연분·점수·성립 판정을 저장해도 된다는 명시적 허용은 이번에 확인하지 못했다. 단순 불리언도 무조건 자유라는 결론은 내리지 않는다.
- **외부 에이전트:** 내부 API 통합 자체를 모두 금지라고 단정하지 않는다. 다만 고객 에이전트의 대화 저장·LLM 요약·재전달까지 현 계약으로 허용되는지는 확정하지 못했다. 모델 학습 금지를 일반 추론 전면 금지와 동일시하지도 않는다. Routes에 LLM용 예외가 자동 적용된다고 볼 근거는 없다. 별도 Maps Grounding Lite의 예외는 Routes에 전용할 수 없다.
- **지도 링크:** Google 결과 옆에 기존 카카오 안내 링크를 그대로 붙이는 구조를 허용 확정하지 않는다. Google 안내 링크로 바꾸는 안을 검토하되, 링크 변경만으로 저장·재전달 문제가 해결되지는 않는다.
- **독립 데이터:** 사용자가 준 일정·좌표·자체 규칙은 Google 응답과 출처가 다르다. 해당 데이터 자체의 권한을 따로 확인하고 관리한다.

이는 공개 조건에 대한 프로젝트 검토이며, 고객별 계약 허용을 확정한 법률의견은 아니다. 확인되지 않은 범위를 허용으로 구현하지 않는다.

## 5. 현재 코드와의 충돌

`modules/mobility/__init__.py`는 비어 있고 운영용 카카오 어댑터는 이 디렉터리에서 발견되지 않았다. 현재는 설계·규칙·수집/검토 스크립트가 중심이다. 따라서 교체는 완성 어댑터의 URL 치환 작업이 아니다.

`final_project_cs/app/application/controller.py:261`은 응답의 answer와 evidence를 이벤트 state_patch에 넣는다. §177에서는 결과 이벤트를 기록 경로로 넘긴다. Google 응답을 Evidence로 보내면 Mobility 내부에서 저장하지 않더라도 코어에 남을 수 있다.

기존 `docs/mobility/2026-09-09_Mobility_모듈설계서_초안v0.2.md`의 '파생값만 저장' 설명은 사용자가 준 최신 카카오 handoff의 정정과 충돌한다. 이번 검토에서 그 문장을 재승인하지 않았고, 기존 카카오 스크립트의 응답 파일 저장 동작도 실행하지 않았다. 기존 파일은 임의 삭제하지 않았다.

## 6. 비용과 다음 도입 조건

기본 Compute Routes Essentials는 월 무료 한도 10,000건, 이후 첫 유료 구간 1,000건당 USD 5다. 해당 SKU로 여행당 30~60건을 호출한다고 가정하면 무료분 소진 뒤 USD 0.15~0.30/여행이다. 재확인·실패·다른 API 비용은 별도다. [가격표](https://developers.google.com/maps/billing-and-pricing/pricing)

요청한 상위 기능에 따라 SKU가 달라진다. 이번 요청에는 알려진 Pro/Enterprise 유발 기능을 넣지 않았지만, 실제 청구 내역은 콘솔에서 확인하지 않았다. [SKU 조건](https://developers.google.com/maps/billing-and-pricing/sku-details)

도입 재판정에 필요한 것은 (1) 서울 독립 보행·차량 데이터 확보, (2) Google 기반 판정 저장·외부 에이전트 전달의 명확한 이용 근거 또는 그 요구를 충족하는 다른 제공자, (3) 코어 로그·Evidence·지도 표시 경계 설계, (4) 실제 운행·보행 검증이다. 현재는 추가 호출 수를 늘려도 저장 허용 범위가 해결되지 않으므로 여기서 전면 교체 판단을 중단한다.
