# 코어 계약 요약 v0.2 — SKN32-FINAL-6TEAM 코드 기준

정본: `final_project_cs/app/core/contracts.py`(2026-09-09 전문 확인), `app/core/remote_team/executor.py`, `app/application/controller.py`. 이 문서는 Mobility 모듈이 지켜야 할 부분과 그 위에 얹는 매핑만 적는다. 계약은 코드가 정본이고, 매핑 중 모듈 경계에 걸린 것만 ◆다. v0.1 대비 바뀐 것: `Evidence`·`ContextPack`·`TeamManifest`·enum 값을 코드로 확인해 매핑을 확정하고, 예시 결과를 붙였다.

## 1 Team이 구현하는 것

```python
@runtime_checkable
class TeamModule(Protocol):
    manifest: TeamManifest
    async def execute(self, task: TeamTask) -> TeamResult: ...
```

`contracts.py`의 이름은 `TeamModule`이다(v0.1의 `TeamExecutorPort`는 `executor.py` 쪽 포트 이름). Team은 `TeamTask` 하나를 받아 `TeamResult` 하나를 돌려주고, side effect는 실행하지 않는다. 타임아웃은 Controller. Core는 Team 내부를 import하지 않는다(`tests/contract/test_core_isolation.py`가 강제).

## 2 TeamManifest — Mobility 등록값(제안)

| 필드 | 제약 | Mobility |
|---|---|---|
| `team_id` / `display_name` | | `mobility` / "이동·동선" |
| `contract_name` / `supported_contract_versions` | `a_cop.team_task` | `["1.0"]` |
| `capabilities` | ≥1 | `mobility.validate_legs`, `mobility.replan_legs`, `mobility.recheck_legs` |
| `accepted_case_types` | | 코어 분류 라벨 확정 후(일정 제출 / 사건 신고 / 확인 요청) ◆ |
| `required_context` | `case_state·policy·db_facts·history` 중 | `["case_state"]` — 시간표는 Team 저장소에서 읽으므로 `db_facts` 불필요 |
| `allowed_tools` | | `kakao_transit_route`, `kakao_walk_route`. 시간표·규칙 표 조회는 모듈 내부 읽기라 tool로 등록하지 않음 |
| `knowledge_scope` | | `["mobility.timetable", "mobility.rules"]` |
| `max_steps` | 1~12, 기본 6 | 6 = 후보 열거 최대 4개(ⓐ~ⓓ) + 최초 검증 + 응답 조립 |
| `implementation_revision` | | git 해시 |

## 3 입력 — TeamTask와 ContextPack

`TeamTask`: `task_id/run_id/case_id`(그대로 반환), `team_id`, `capability`(검증/재계획/재확인 분기), `case_version`, `input_text`(≤12,000, 고객 신고 원문), `context: ContextPack`, `allowed_tools`, `deadline_at`, `resume/resume_node`. 검증기: `resume=True`면 `resume_node` 필수, `context.case_id/team_id`는 task와 일치.

`ContextPack`(`extra="forbid"`): `pack_id, case_id, team_id, tenant_id, knowledge_scope, current_state: dict, evidence ≤40, history_summary ≤10,000자, similar_cases ≤3, token_budget=12000 고정, estimated_input_tokens, degraded, omissions`. 예산을 넘긴 팩은 만들어지지 않고, `degraded=True`면 `omissions`가 필수다.

→ **구조화 입력은 전부 `current_state`에 실려야 한다.** 필드를 추가할 수 없다. 시간표는 예산 안에 못 실으므로 Mobility 저장소에서 읽는다. `current_state` 안의 키는 Controller/ContextBroker가 넣어줘야 하므로 ◆다. 제안:

```json
"current_state": {
  "trip": {"trip_id": "...", "schedule_version": 7, "date": "2026-10-03", "language": "en"},
  "stage": "planning | pre_departure | in_progress",
  "current_location": {"lat": 37.56, "lng": 126.98, "observed_at": "..."},
  "party": {"size": 2, "infant": true, "luggage": true, "fatigue": "normal"},
  "legs": [{"leg_id": "L3", "from": {"name": "Myeongdong Kyoja", "lat": 37.562, "lng": 126.985},
            "to": {"name": "Gyeongbokgung", "lat": 37.579, "lng": 126.977},
            "depart_at": "14:20", "arrive_by": "15:00", "arrive_fixed": true, "locked_booking_id": null}],
  "replan": {"affected_leg_ids": ["L3"], "cause": "activity_cancelled | service_disruption", "changed": {...}, "exclude": [],
             "disruption": {"lines": ["04호선"], "stations": ["명동"], "direction": null,
                            "from": "2026-10-03T14:00", "to": null, "kind": "no_stop | delay | suspended",
                            "source_id": "...", "observed_at": "..."}},
  "previous_verdicts": [{"leg_id": "L3", "verdict": "ok", "checked_at": "..."}]
}
```

`stage`·`current_location`이 없으면 Mobility는 시각·마지막 완료 장소로 자체 추정하고 decisions에 `stage_assumed=true`를 남긴다(담당 결정).

`replan.disruption`은 **운행 이슈 감지를 코어가 맡기로 한 9/9 합의**에 따라 새로 제안하는 키다. Mobility는 소스를 직접 보지 않고 이 다섯 가지(영향 노선·역·방향, 시작/종료 시각, 원인 구분, 소스 ID, 확인 시각)만 있으면 해당 노선을 제외하고 재판정한다. 이슈 자체의 Evidence는 코어가 `case_event`로 만들고 Mobility는 `rationale_evidence_ids`로 인용만 한다. 소스 후보는 소싱 문서 §3-11.

## 4 Evidence — 근거 등급·확인 시각을 싣는 자리

```
Evidence(evidence_id, source_type ∈ {customer_message, db, policy, tool_result, case_event, remote_agent},
         source_id, claim, value: Any, confidence 0~1, observed_at: datetime)   # 전부 의무, extra=forbid
```

| 설계 개념 | 계약의 자리 |
|---|---|
| 소스 이름 | `source_id` — `tago_subway@2026-09-09`, `mobility_rules@v0.1`, `kakao_transit_route` |
| 확인 시각 | `observed_at` — 시간표는 **수집일**(`fetched_at`), 규칙은 개정일, 카카오는 호출 시각 |
| 근거 등급 **확정** | Evidence가 존재(`db`/`policy`), `confidence` 0.9~1.0, `value.grade="확정"` |
| 근거 등급 **근거 없음** | Evidence를 만들지 않는다. `decisions[].evidence_grade="근거없음"` + `warnings`에 사유 |
| 값 등급 **추정** | `tool_result` Evidence, `value.grade="추정"`, `confidence` 0.5~0.7. value는 파생값만(소싱 문서 3-3) |
| 판정 이력 | `case_event`, `source_id=mobility_verdict@<이전 task_id>` — 재확인 때 비교 근거 |

`evidence_id`는 `mob:{leg_id}:{kind}:{n}`처럼 결정적으로 만든다. 제안(`ActionProposal.rationale_evidence_ids`)이 가리키는 id는 같은 결과의 `evidence` 안에 있어야 한다(검증기).

## 5 출력 — TeamResult와 ActionProposal

`TeamResult`: `outcome ∈ {completed, waiting, handoff, escalated, failed}`, `answer ≤6,000`, `confidence`, `evidence[]`, `decisions[dict]`, `action_proposals[]`, `next_action ∈ {continue, wait_for_input, wait_for_approval, call_tool, handoff, respond, escalate}`, `wait_reason ∈ {customer_input, human_approval, external_callback}`, `required_input_schema`, `handoff_capability`, `failure_code`, `warnings[]`.

검증기가 강제하는 것: `answer`가 있으면 `evidence` 비면 안 됨 / `wait_for_input`은 `wait_reason=customer_input`+`required_input_schema` / `wait_for_approval`은 `human_approval`+제안 ≥1 / `handoff`는 `handoff_capability` / `respond`는 `answer` / `escalate`는 `failure_code` 또는 `warnings` / **`approval_required=True` 제안이 하나라도 있으면 `next_action`은 반드시 `wait_for_approval`**.

`ActionProposal`: `action_type, arguments: dict, idempotency_key(서버 재계산), approval_required, risk_level ∈ {low, medium, high}, rationale_evidence_ids`. 대안의 내용은 전부 `arguments`에 담는다.

`decisions[]` 항목(자유 dict, Mobility 정의):

```json
{"leg_id": "L3", "verdict": "ok | fail | unknown", "evidence_grade": "확정 | 근거없음",
 "reasons": ["2호선 하행 막차 23:52, 도착 필요 23:40 이후 출발"], "relax": ["출발을 22:50으로 당기면 성립"],
 "estimate": {"duration_min": 30, "arrive_est": "14:50~14:55", "transfers": 1, "walk_m": "500~800", "grade": "추정"},
 "link": "https://map.kakao.com/link/by/traffic/Myeongdong Kyoja,37.562,126.985/Gyeongbokgung,37.579,126.977",
 "evidence_ids": ["mob:L3:timetable:1", "mob:L3:route:1"], "alternative_ids": ["alt:L3:1"], "stage_assumed": false}
```

## 6 Controller.run_case에서 확인된 것

1. ROUTING이면 `registry.resolve(case_type, intent)` → **Team 하나** 배정. 여러 Team 동시 호출·합류 로직은 `run_case`에 없다. `self.broker`는 주입되지만 `run_case`에서 쓰이지 않는다.
2. `_task()`가 TeamTask를 만들고(ContextPack은 ContextBroker), `team_executor.execute` 타임아웃 시 escalated.
3. `_maybe_review`: 응답 검수 Team이 켜져 있으면 Controller가 만든 `task.context`로 answer를 대조한다(Team의 context는 신뢰하지 않음).
4. `_apply_result` → 상태 전이 → `next_action` 반환. Team 간 이동은 `next_action=handoff`+`handoff_capability`.

→ Mobility 결론: "액티비티 취소 → 이동 재검증"은 Activity Team의 handoff 또는 새 케이스로 온다. Mobility는 자기 구간 대안까지만 내고 **다른 Team 영향 판단은 코어에 맡긴다**(handoff 대상을 Mobility가 고르지 않는다). 검증기 규칙상 승인 필요 제안과 handoff를 한 결과에 같이 담을 수도 없다.

## 7 Mobility 매핑

| capability | 상황 | outcome / next_action | 담기는 것 |
|---|---|---|---|
| `mobility.validate_legs` | 판정 완료 | completed / respond | `decisions` 구간별 판정, `evidence`, `answer` 요약 |
| | 모든 구간 근거 없음 | escalated / escalate | `failure_code=MOBILITY_NO_EVIDENCE`, `decisions`는 채움, `answer` 없음 |
| `mobility.replan_legs` | 통과한 대안 있음 | completed / respond **또는** waiting / wait_for_approval | `action_proposals`(`mobility.replace_leg`·`shift_departure`·`drop_leg`). 승인 필요 여부는 아래 ◆ |
| | 대안 없음 | completed / respond | `decisions[].verdict=fail`, `relax`만, "이 구간 불가" |
| `mobility.recheck_legs` | 변화 없음 | completed / respond | `decisions[].changed=false`, 카카오 호출 0 |
| | 변화 감지 | replan과 같음 | `decisions[].changed=true` + 이전 판정 `case_event` 근거 |
| | 판단 불가 | escalated / escalate | `warnings`(시간표 미확보 등) |
| 진행 중 현재 위치 필요 | | waiting / wait_for_input | `wait_reason=customer_input`, `required_input_schema={current_location}` |

**approval_required 정책 ◆** — 팀장 문서의 선제 조정은 "우리가 바꾸고 통지, 고객은 거부권"이다. 담당 제안: 잠긴 예약에 닿지 않는 이동 대안은 `approval_required=False`(risk low/medium)로 내고 코어가 적용·통지한다. 잠긴 예약 시각을 바꿔야 하는 대안(앞 일정 단축·출발 조정이 예약에 걸림)은 `approval_required=True`, `risk_level=high`. 이 경계가 코어 정책과 맞는지가 합의 항목이다.

## 9 아직 코드에서 안 본 것

`TeamRegistry.resolve`·`capability_for`(intent → capability 규칙), `Controller._task`(ContextPack 조립 — `current_state` 키를 누가 채우나), `_apply_result`(approval 대기 전이·action_proposals 처리), `executor.py`의 `TeamExecutorPort`와 `TeamModule` 관계, tool 등록·`ToolNotAllowed` 검사 지점, `MessageBrokerPort`가 재확인 스케줄에 쓰이는지. 검색어: `def resolve`, `def capability_for`, `def _task`, `def _apply_result`, `ToolNotAllowed`, `OutboxBrokerAdapter`.
