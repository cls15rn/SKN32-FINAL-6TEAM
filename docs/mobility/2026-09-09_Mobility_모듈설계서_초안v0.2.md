# Mobility(이동·동선) 모듈 설계서 초안 v0.2

작성일: 2026년 9월 9일 (v0.1: 9월 8일) · 담당: 서유현

코어가 배정한 이동 요청을 받아 "이 구간 이동이 그 시각에 성립하는가"를 판정하고, 성립하지 않으면 사유·완화 조건·대안 구간을 근거와 함께 반환하는 Mobility 모듈의 독립 설계 문서다. 팀장의 후보 검토 문서(9/8), Dining 모듈 설계서 초안 v1, 그리고 코어 계약 코드(`contracts.py`, 9/9 확인 — 요약은 `2026-09-09_코어계약_요약_v0.2.md`)를 기준으로 한다. 짝 문서: `이동모듈_아키텍처_v0.2.html`(그림), `2026-09-09_Mobility_데이터소싱_v0.2.md`(데이터).

v0.1에서 바뀐 것: ① 재확인 타이머를 모듈 밖으로 확정하고 "감시기"를 "재확인 처리"로 고침 ② 근거 등급·확인 시각을 계약의 `Evidence`에 매핑 ③ 코어가 케이스 하나를 Team 하나에 배정한다는 코드 확인을 반영해 사건 흐름을 handoff/코어 판단 기준으로 고침 ④ ◆를 3개로 재정리 ⑤ **팀 피드백(9/9 오후) 반영 — 환승 여유 고정값 삭제(이중 계산). 카카오 보행 속도를 실측(1.04 m/s)해 보정 계수를 다시 계산하고, 길찾기 시간을 계수에서 분리했다. 규칙은 `config/mobility/rules_v0.2.json`으로 분리. ⑥ **운행 이슈(사고·화재·무정차·통제) 감지는 코어 담당으로 확정** — Mobility는 소스를 직접 보지 않고 계약으로 받는다(9절).** 함수명·필드·수치는 제안이며 모듈 내부 결정은 담당이 정하고 이유를 9절에 적었다.

## 1 연동 흐름과 Mobility의 범위

코어(Controller)가 케이스를 분류·라우팅해 **Team 하나**에 `TeamTask`를 주고 `TeamResult`를 받는다. Mobility는 한 번 처리하고 결과를 반환한다. 다른 Team을 직접 부르지 않고, 필요한 정보는 `ContextPack.current_state`에 실려 온다. 다른 Team으로의 영향 전파(액티비티 취소 → 이동 재검증)는 코어의 handoff·재라우팅이 맡고, 재확인 시점을 정하는 타이머도 코어(공통 스케줄러) 쪽이다 ◆.

| Mobility가 받는 것 | 처리하는 것 | 반환하는 것 |
|---|---|---|
| 구간(양 끝 좌표·장소명), 시각 제약(출발/도착 필요, 고정 여부), 동행 조건, 단계·현재 위치, 이전 판정 | 경로 조회(필요 시), 그 시각의 성립 여부(첫차·막차·배차), 여유·환승·도보 조건 판정 | 구간별 성립/불가/판단 불가, 사유, 완화 조건, 근거(Evidence), 카카오맵 링크 |
| 영향 구간과 바뀐 제약, 원인, 제외 후보 | 대안 후보 열거 → 같은 검증 재통과 | 통과한 대안 1~2개(ActionProposal), 없으면 "이 구간 불가" |
| 재확인 요청(코어 스케줄러가 배정 ◆) | 시간표 기준 재판정, 이전 판정과 비교 | 변화 없음 / 변화 감지(+대안) / 판단 불가 |
| **운행 이슈**(사고·화재·무정차·통제) — 코어가 감지해 `current_state.replan`/`input_text`로 전달 | 영향 구간을 이슈 조건으로 재판정, 해당 노선 제외 후 대안 열거 | 성립/불가 + 대안, 이슈를 `Evidence`(source_type=`case_event`)로 인용 |

식당·액티비티·숙소를 고르지 않는다. 일정 순서 재배열·앞 일정 단축·예약 실행·통지 발송은 코어 또는 다른 담당의 범위이며 Mobility는 제안만 한다. 경로 상세는 카카오맵 링크로 대신하고 판정만 넘긴다.

## 2 구성

| 구성 | 담당 | 구현 |
|---|---|---|
| 요청 라우터 | `capability`로 검증/재계획/재확인 분기, 계약↔내부 어댑터, 단계별 파라미터 | 일반 코드 |
| 경로 조회 어댑터 (tool) | 카카오 대중교통·도보 경로 호출. 응답은 처리 중 메모리만, 캐시 없음 | requests, `allowed_tools`에 등록 |
| 시각 검증기 | 요청 시각에 그 경로의 노선이 운행하는지. **수단별로 분기한다** — 지하철은 열차 단위 시간표라 "그 시각에 출발하는 차가 있는가", 버스는 노선 단위(첫차·막차·배차간격)라 "운행 구간 안인가 + 배차만큼 대기" | 규칙 코드 |
| 제약 대조 판정기 | 카카오가 준 소요를 **우리 제약과 대조**하고, 카카오가 **아예 주지 않는 것만 더한다** — 차를 기다리는 시간(시간표), 초행 길찾기, 정책 버퍼. 도보 시간은 MVP에서 그대로 쓰고 긴 도보 + 느린 동행이면 경고만 남긴다 | 규칙 코드 + `rules_v0.2.json` |
| 근거·판정 조립 | `Evidence`(확정 기록·추정 파생값·규칙) + `decisions`(구간별 판정) + 링크 | 일반 코드 |
| 후보 열거 | 대안 후보를 규칙 순서로 열거하고 검증을 재통과시킴 | 규칙 코드, LLM 없음 |
| 재확인 처리 | 배정된 재확인 요청을 시간표로 재판정하고 이전 판정과 비교. **타이머는 갖지 않는다** | 규칙 코드 |
| 저장소 | 시간표(processed), 규칙 표, 구간 판정 이력(판정·확인 시각·소스 이름만) | SQLite/JSONL로 시작 |

LLM은 판정 경로에 들어가지 않는다. `answer` 문장은 구조화 결과에서 템플릿으로 만들고, 자연어 다듬기는 답변 생성 쪽 몫이다.

## 3 업무 함수 세 개

진입점은 `MobilityTeam.execute(task) -> TeamResult`(계약)이고, 안에서 `capability`별로 나눈다.

| capability | 함수 | 주된 반환 |
|---|---|---|
| `mobility.validate_legs` | `validate_legs(legs, ctx)` | 구간별 판정 + Evidence + 링크 → respond |
| `mobility.replan_legs` | `replan_legs(legs, trigger, ctx)` | 통과한 대안 ActionProposal 1~2개, 없으면 불가 |
| `mobility.recheck_legs` | `recheck_legs(legs, ctx)` | unchanged / change_detected(→ replan) / unresolved |

`replan_legs`와 `recheck_legs`는 후보를 열거해 `validate_legs`를 반복하는 함수이지 별도 엔진이 아니다. `build_guidance`(링크 조립·문장 템플릿)는 셋이 공유한다.

## 4 검증 흐름(F1)

입력 예: 구간 "명동교자 → 경복궁", 출발 14:20, 다음 일정 15:00 고정, 유아 1명.

1. **라우터** — `capability`와 `current_state.stage`로 파라미터 세트를 고른다(진행 중: 후보 2개, 현재 위치 반경, 버퍼 15분, 택시 허용). `stage`·`current_location`이 없으면 시각·마지막 완료 장소로 추정하고 `stage_assumed=true`를 남긴다.
2. **경로 조회** — 경로 모양·소요시간이 필요할 때만 카카오를 부른다. 재확인은 시간표만으로 끝나므로 부르지 않는다.
3. **시각 검증** — 카카오 응답에는 시각이 없다. 먼저 **여행 날짜로 시간표를 고른다**(평일 / 토·일·공휴일 — 공휴일 판정은 `config/mobility/holidays_*.json`, 규칙은 `rules_v0.2.json`의 `day_type`). 그다음 출발 시각(또는 도착 필요 시각에서 역산)에 그 노선이 운행하는지 시간표에서 본다. 막차 이후·첫차 이전·배차 공백이면 불가. 시간표 없는 노선이면 **근거 없음**.
4. **제약 대조** — 카카오가 주는 것은 고치고, 주지 않는 것은 더한다.

   | 항목 | 카카오 | 우리 |
   |---|---|---|
   | 걷는 시간 | 준다 (1.04 m/s 가정, 실측) | **MVP는 그대로 쓴다.** 보정 계수는 확장 항목 |
   | 타는 시간 | 준다 | 손대지 않는다 |
   | **차를 기다리는 시간** | **주지 않는다** (실측 확인) | 시간표의 그 시각 배차로 채운다. 평균은 배차의 절반, 막차 근처·진행 중은 배차 전부 |
   | 초행 길찾기 | 주지 않는다 | 환승 1회당 1분, 대형 환승역 +2분 |
   | 정책 버퍼 | 주지 않는다 | 10분(진행 중 15분) |
   | 이 일행에게 무리인가 | 말하지 않는다 | 환승·도보 상한 초과 시 성립해도 탈락(불가와 구분) |

   **MVP는 카카오 도보 시간을 그대로 쓴다.** 카카오 기준선 1.04 m/s가 성인 평균 1.3보다 25% 느려 보통 일행에는 이미 여유가 있고, 보정 계수는 전부 [추정]이라 판정이 틀렸을 때 원인을 시간표·버퍼·계수 중에서 가릴 수 없다. 느린 일행의 도보 손실은 버퍼가 흡수하되, **도보 10분을 넘는 구간에 유아·고령·짐·피로 조건이 있으면 `warnings`로 표시한다**(유아 계수 1.5 기준 과소평가가 5분을 넘어 기본 버퍼의 절반을 먹는 지점). 계수 값과 근거는 규칙 파일에 남겨 두고 확장 때 `enabled`만 켠다.

   **환승 도보 시간을 따로 더하지 않는다.** 카카오 `totalTime`에 이미 들어 있어 고정값을 더하면 같은 시간을 두 번 센다(팀 피드백 9/9). 우리가 고치는 것은 시간의 양이 아니라 그 시간이 가정한 **속도**이며, 카카오가 비워둔 자리(대기·길찾기·버퍼)만 채운다.
5. **근거·판정 조립** — 시간표·규칙은 `Evidence(db/policy, 확정)`, 카카오 파생값은 `Evidence(tool_result, 추정)`. 근거 없음은 Evidence를 만들지 않고 `decisions[].evidence_grade`와 `warnings`에 남긴다. 확인 시각은 시간표 수집일·규칙 개정일·호출 시각.
6. **응답 조립** — `decisions`(성립/불가·사유·완화 조건·추정치·링크·근거 id) + `answer` 요약 + `next_action`. 모든 구간이 근거 없음이면 `escalate`.

## 5 사건 흐름(F3)

**남이 일으킨 사건.** 액티비티 취소·식당 변경으로 시각·좌표가 바뀌면 코어가 `mobility.replan_legs`로 영향 구간·바뀐 제약·원인을 `current_state.replan`에 실어 보낸다(Activity Team의 handoff 또는 새 케이스 — 경로는 코어가 정한다 ◆). Mobility는 후보를 순서대로 열거한다 — ⓐ 같은 수단 다른 노선 → ⓑ 수단 변경(지하철↔버스→택시→도보) → ⓒ 출발 시각 조정(앞 일정 단축은 제안만) → ⓓ 목적지 포기("이 구간 불가"만 보고). 각 후보를 4절에 다시 통과시켜 살아남은 1~2개를 `ActionProposal`로 낸다. `max_steps=6` 안이다.

**이동이 일으킨 사건.** 재확인에서 변화가 잡히거나 고객이 "막차 놓쳤다"고 알리면(`input_text`), `decisions[].changed=true`와 대안을 함께 반환한다. **다른 Team에 영향이 가는지의 판단과 전파는 코어가 한다.** Mobility가 handoff 대상을 고르지 않는 이유: 코어는 케이스 하나를 Team 하나에 배정하고, 승인 필요 제안과 handoff를 한 결과에 같이 담을 수 없다(계약 검증기). Mobility는 "새 도착 예상·살릴 수 있는 뒤 일정 여부"를 `decisions`에 적어 코어가 판단할 재료만 준다.

## 6 재확인 흐름(F2)

Dining과 같이 Mobility는 주기 감시를 갖지 않는다. 공통 스케줄러(출발 전날·당일 아침·예약 2시간 전)가 코어를 통해 `mobility.recheck_legs`를 배정한다고 가정한다 ◆. 재확인은 시간표 기준이라 카카오 호출 0으로 돌고, 이전 판정 이력(`case_event` 근거)과 비교해 달라졌을 때만 5절로 넘어간다. **운행 이슈는 Mobility가 감지하지 않는다.** 사고·화재·무정차·통제는 코어가 확인해 `current_state.replan`(영향 노선·역·시각·원인) 또는 `input_text`로 넣어 주고, Mobility는 그 조건을 판정 입력으로 받아 해당 노선을 제외하고 재판정한다. 이슈 자체는 코어가 준 `case_event` 근거로 인용만 하고 우리가 만들지 않는다. 소스 후보는 소싱 문서 §3-11에 코어 인계용으로 적어 두었다.

## 7 입력과 반환

계약 위에서 Mobility가 정의하는 것은 두 곳뿐이다. `ContextPack.current_state`의 키(입력, 계약 요약 3절 — 코어가 채우므로 ◆)와 `TeamResult.decisions[]`·`ActionProposal.arguments`의 내용(출력, 계약 요약 5절). 카카오 응답의 원값(정류장·경로 좌표·요금·소요 원값)은 어디에도 넣지 않는다. 판정·파생값·링크만 나간다.

## 8 데이터

규칙 표는 `config/mobility/rules_v0.2.json`(값마다 grade·근거 포함, `rules_check.py`로 검사. 보행 기준선은 `probe_kakao_walk.py` 실측). 데이터 상세는 `2026-09-09_Mobility_데이터소싱_v0.2.md`. **수집 상태(9/9)**: 지하철 시간표 465,490행(서울 1~9호선 100%, TAGO + 열린데이터광장 보충), 공항 리무진 8,949행(180노선), 역 좌표 793/799. 시내버스는 승인 대기(서울 data.go.kr 15000193, 인천·경기 TAGO). 카카오는 호출만·저장 없음, 규칙 표는 `policy` 근거.

**수단별로 확정도가 다르다.** 지하철과 **공항 리무진**은 출발 시각 목록이 있어 시각 자체가 확정이다(리무진 180노선 중 121개, 나머지는 첫차·막차만 → 근거 없음). 시내버스는 노선 단위라 첫차~막차 구간은 확정이지만 대기는 배차 평균이라 추정이고, 서울 `term`은 노선당 값 하나여서 시간대별 차이도 못 담는다 — 그래서 막차 근처에는 배차 전부를 대기로 잡는다. 운행 이슈(사고·화재·무정차)는 **코어가 확인해 넘겨주는 입력**이므로 Mobility의 데이터 범위 밖이다 — 우리는 이슈 조건이 들어왔을 때의 재판정만 책임진다(6절). 시연은 코어 입력 형태의 Mock으로 한다. 남은 미확보(김포 리무진·택시)는 "근거 없음"·"소요 판단 불가"로 반환하고 확보되면 어댑터만 추가한다.

준비 순서: ① 지하철 시간표 보정 마무리 → ② 공항버스·시내버스·역 좌표 수집 → ③ 규칙 표 파일화 → ④ 합성 여행 20~30건 구간으로 검증기 확인(지하철·버스 두 분기) → ⑤ 코어가 주는 이슈 입력 형태의 Mock으로 F3 → ⑥ 택시는 확보되면 어댑터만 추가.

## 9 담당 결정과 이유

| 결정 | 이유 |
|---|---|
| 대안 생성은 규칙 열거, LLM 없음 | 후보 공간이 노선·수단·시각·포기 넷으로 닫혀 있다. LLM은 없는 노선을 지어낼 위험만 늘고 규칙 후보는 시간표로 즉시 검증된다. 팀장 원칙 "대안 생성 = LLM"은 후보가 열린 Activity·Dining에 맞고 Mobility는 예외 |
| 구간 판정 이력은 모듈 내부 보관 | 코어 상태엔 결과만. 근거·확인 시각·소스 이름을 모듈이 가져야 재확인에서 "달라졌나"를 모듈 안에서 비교한다 |
| 등급을 근거/값으로 분리 | 시간표대로 오는 차는 없으므로 도착 시각 확정은 성립하지 않는다. 확정은 기록 자체, 값은 항상 추정, 버퍼가 오차 흡수 |
| **근거 없음은 Evidence를 만들지 않는다** | 계약의 Evidence는 출처가 있는 주장이다. "없다"를 Evidence로 만들면 근거 대조에서 확정과 섞인다. `decisions`+`warnings`로 남기고 전 구간 근거 없음이면 escalate |
| **카카오 근거는 파생값만** | 약관(응답 저장·캐시 금지)과 에이전트가 제3자인지 회색. 판정에 필요한 요약값은 우리 판정이고 원값은 남기지 않는다 |
| **타이머는 모듈 밖** | Dining도 갖지 않고, 코어 계약에 스케줄 개념이 없다. 모듈은 `recheck_legs` capability만 노출한다 |
| **운행 이슈 감지는 코어** | 팀 합의(9/9). 이슈는 이동만의 문제가 아니라 액티비티·예약에도 동시에 걸리고, 한 소스를 여러 모듈이 각자 폴링하면 판정 시각이 갈린다. 타이머가 모듈 밖인 것과 같은 이유 — 주기 조회 주체는 하나여야 한다. Mobility는 이슈 조건을 받아 재판정하는 쪽만 맡는다 |
| **다른 Team 영향 판단은 코어** | run_case가 Team 하나만 배정하고 handoff 대상을 Team이 고르면 Team 간 결합이 생긴다. Mobility는 판단 재료(새 도착 예상·뒤 일정 여부)만 준다 |
| **단계·현재 위치 부재 시 자체 추정** | 코어가 못 채우는 경우에도 판정은 나가야 한다. `stage_assumed=true`로 표시해 정직성을 지킨다 |
| 승인 정책 기본값 제안 | 잠긴 예약에 닿지 않는 대안은 `approval_required=False`(선제 조정·거부권 모델), 잠긴 예약을 건드리면 True·high. 경계는 ◆ |
| **환승 고정 여유 5분 삭제** | 카카오 `totalTime`에 환승 도보가 이미 포함돼 있어 이중 계산이었다. 팀 피드백(9/9)이 맞다 |
| **보행 속도는 재서 정했다 (1.04 m/s)** | "카카오 도보 시간은 노약자까지 고려한 값"이라는 의견을 논쟁 대신 측정으로 갈랐다. 도보 API 6구간의 거리÷시간 중앙값 1.04 m/s(범위 1.01~1.10, 편차 0.09라 고정 속도 모델). 서울시 일반 보행신호 기준 1.0에 가깝고 성인 평균 1.3보다 25% 느리다 — **보통 성인보다 느린 건 맞지만 노약자 기준(0.7)은 아니다** |
| **MVP는 보정 계수를 쓰지 않는다** | 위 실측이 "보통 일행에는 이미 여유가 있다"를 보여 준다. 계수는 전부 [추정]이라 MVP에 넣으면 판정 오류의 원인을 가릴 수 없고, 7주 일정에서 이동 모듈은 세 번째다. 규칙 파일에 `walk_pace.enabled=false`로 두고 값·근거는 남긴다 |
| **확장 트리거는 나이·성별이 아니라 동행 조건** | 유아차를 미는 30대가 유아차 없는 65세보다 느리다. 나이·성별은 보행 속도의 대리 변수로 부정확하고, 인바운드 외국인 대상 서비스에서 수집 부담도 크다. 계약의 `current_state.party`에 이미 자리가 있으므로 그 값이 채워지면 `enabled`만 켜면 된다 |
| **끈 대신 경고를 남긴다** | 보정을 끄면 과소평가가 도보 시간 × (계수−1)만큼 생긴다. 유아 기준 도보 10분에서 5분이라 기본 버퍼 10분의 절반이다. 그 이상 구간에만 `warnings`를 남겨, 짧은 도보에서는 안전하고 긴 도보에서만 위험하다는 사실을 판정에 드러낸다 |
| **길찾기 시간을 계수에서 분리** | v0.1의 초행 기본 계수 1.15는 사실 속도가 아니라 표지를 찾는 시간이었다. 그건 걷는 거리에 비례하지 않으므로 곱셈이 아니라 환승당 고정 가산(1분)이 맞다 |
| **대기 시간은 카카오에 아예 없다** | 실측: `totalTime` 2045s = 버스 step 883s + 나머지 1162s이고 나머지 구간의 함의 속도가 1.06 m/s로 도보와 일치한다. 즉 걷는 시간 + 타는 시간뿐이고 기다리는 시간이 없다. 우리가 시간표로 대기를 채우는 것은 이중 계산이 아니라 빈 자리를 메우는 것이다 |
| **보정 계수는 최대값 하나만** | 요인을 곱하면 유아+짐이 1.8배로 과해진다. 가장 느린 사람이 일행 전체의 속도를 지배한다 |
| **환승 실패 페널티 = 갈아탈 노선 배차간격** | 고정 5분이 아니다. 2호선은 3분, 경의중앙선은 20분이라 판정이 뒤집힌다. 시간표가 있어야 계산되고 경로 API는 출발 시각을 못 받아 주지 못한다 — 시간표를 따로 모은 이유가 여기서 증명된다 |
| 규칙 초기값 | 버퍼 10분(진행 중 15분), 유아·짐 도보 상한 800m, 환승 상한 2회(유아·고령·피로도 1회), 길찾기 환승당 1분, 대형 환승역 +2분, 도보 경고 10분. 보행 기준선만 [확정](실측)이고 나머지는 [추정]이라 합성 여행 20~30건으로 조정. 값·근거·grade는 `config/mobility/rules_v0.2.json`에 있고 `rules_check.py`가 검사한다 |
| 판정만 전달, 상세는 링크 | 에이전트로는 판정·근거·확인 시각만, 경로 상세는 우리가 조립한 카카오맵 링크(호출 0). 예약 링크 원칙과 같은 모양 |

## 9-1 확장 항목 (MVP 제외, 근거는 만들어 둠)

| 항목 | 켜는 조건 | 준비 상태 |
|---|---|---|
| 보행 속도 보정 계수 | 개인 에이전트에서 동행 조건(유아·고령·짐·피로)이 `current_state.party`로 넘어올 때 | 값·근거 계산 완료(실측 1.04 m/s 대비 비율). `walk_pace.enabled`만 true로 |
| 환승 정밀 모델 | 카카오 `steps[]`에 구간별 시각이 오거나 자체 경로 계산으로 넘어갈 때 | 지금은 배차의 절반/전부 근사. 도착 시각을 알면 시간표에서 다음 열차를 직접 찾는다 |
| 택시 대안의 소요 | 카카오모빌리티 자동차 길찾기 등록 시 | 지금은 후보 열거만 하고 소요는 판단 불가 |
| 운행 이슈 대응 | 코어가 이슈 입력(`current_state.replan`) 규격을 확정할 때 | 판정 쪽은 대안 열거로 이미 처리 가능. 소스 후보는 소싱 문서 §3-11에 코어 인계용으로 정리 |

## 10 합의 필요 ◆ (3개)

1. **재확인·재계획 요청의 발신 경로** — 공통 스케줄러와 사건 전파가 코어의 어느 자리에서 `mobility.recheck_legs`/`replan_legs`를 배정하는가(run_case 재라우팅 vs 브로커 vs Activity handoff). Mobility는 어느 쪽이든 같은 계약으로 받는다.
2. **`ContextPack.current_state` 키** — 구간·시각 제약·동행 조건·단계·현재 위치·재계획 문맥(계약 요약 3절 제안). ContextBroker가 채워야 하는 항목.
3. **이동 대안의 `approval_required` 정책** — 9절 기본값 제안이 코어의 선제 조정·승인 정책과 맞는지.

계약 이름·필드는 코드 확인 사항이지 합의 대상이 아니다(v0.1 ◆3 "change_detected 반환 형태"는 `decisions`·`ActionProposal`로 해소).

## 11 개발 순서와 확인 사례

| 순서 | 구현할 묶음 | 단독 완료 기준 |
|---|---|---|
| 1 | 시간표 저장소(processed 로더) + 시각 검증기 | 막차 이후·첫차 이전·배차 공백·시간표 없는 노선을 구분. 지하철(열차 단위)·버스(구간+배차) 분기 |
| 2 | 여유·조건 판정기 + 규칙 표 파일 | 버퍼 부족, 환승·도보 상한 초과를 사유와 함께 반환 |
| 3 | Evidence·decisions 조립 + 카카오맵 링크 | `TeamResult` 검증기 통과, 근거 id 정합, 원값 비노출 |
| 4 | 카카오 어댑터 | 경로 조회 → 판정까지 한 구간 완주, 실패 시 소요 "판단 불가" |
| 5 | 후보 열거 + 재검증 반복 | 막차 경과 시 수단 변경·시각 조정 대안이 검증을 통과해 `ActionProposal`로 |
| 6 | 재확인 처리 | 이전 이력과 비교해 unchanged / change_detected / unresolved |
| 7 | 합성 여행·사건 시나리오 | 20~30건 구간에서 판정·대안·링크가 구조화 결과와 일치 |

확인 사례: 막차 경과 → 불가 + 완화 조건 + 택시 대안 / 유아 동반 + 환승 3회 → 성립하지만 탈락, 환승 1회 대안 / 시간표 없는 노선 → 근거 없음, 정상으로 바꾸지 않음 / 카카오 실패 → 성립 여부는 내고 소요는 판단 불가 / 재확인 변화 없음 → 호출 0으로 unchanged / 전 구간 근거 없음 → escalate.

코어 검증 통과율, 라우팅 정책, 통지 발송은 Mobility 완료 기준에 넣지 않는다.
