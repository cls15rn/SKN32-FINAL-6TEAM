# 항공편 항목의 채팅 결함 확인과 고침 (2026-10-15)

결론: 항공에도 숙소(LB-02)와 **같은 결함이 있었다** — 재현했다. 채팅의 「항공 다른 편으로 보여 줘」는 항공 팀이 아니라 활동 팀으로 넘어가 「요청을 완료하지 못했어요」로 끝났다. 숙소와 같은 방식으로 고쳤고 회귀 시험을 더했다. **x600 서버에서는 확인하지 못했다** — 아직 배포 전이다.

| 할 일 | 상태 | 진행 |
|---|---|---|
| 항공 채팅 결함 재현 | 끝 | 4/5 시험이 고치기 전에 실패(재현) |
| 고침 5곳 | 끝 | 5/5 = 100% (각각 끄면 시험이 실패) |
| 회귀 시험 | 끝 | 새 6개 + 규칙 경로 1개 |
| mock 서버 시험(화면 반응) | 해당 없음 | 화면 코드는 안 바꿨다 |
| 실서버 확인(x600 서버 응답) | 안 했음 | 0/1 = 0% |

## 고객에게 달라지는 것

항공편이 든 여행에서 채팅으로 「항공 다른 편으로 보여 줘」라고 하면 항공 팀이 새 편 3개를 「선택이 필요해요」 제안으로 낸다(일정은 고를 때 바뀐다). 전에는 사람에게 넘어가는 오류로 끝났다.

## 재현과 원인

재현(웹 채팅 종단, 해석 모델 · 항공 검색은 고정 대역): 「항공 다른 편으로 보여 줘」 → `escalated`, 「요청을 완료하지 못했어요」. 숙소와 같은 모양이다. 원인도 숙소와 같고 하나가 더 있었다.

| | 어디서 | 무슨 일 | 고침 |
|---|---|---|---|
| ① | [trip_messages.py](../../../app/domains/travel_ops/components/conversation/trip_messages.py) `_dispatch_decision` | 담당 팀을 정하는 표(`ITEM_TEAMS`)에 항공이 없어 항공편 항목이 담당 없이 **활동 팀**으로 넘어갔다 | `ITEM_TEAMS` 에 `flight` |
| ② | [conversation_work.py](../../../app/domains/travel_ops/instances/_shared/conversation_work.py) · [flight/team.py](../../../app/domains/travel_ops/instances/flight/team.py) | 항공 팀에 닿아도 공용 처리가 식당 · 활동의 장소 목록으로 계획해 항공 팀 자신의 「바꿔 줘」(`FlightTeam._change`)는 웹 채팅에서 불린 적이 없었다 | 숙소 때 만든 선언(`conversation_change_by_team`)을 항공 팀도 켰다 — 공용 처리 코드는 그대로 |
| ③ | [case_dispatch.py](../../../app/domains/travel_ops/components/conversation/case_dispatch.py) · flight/team.py | 되묻기 번호 고르기에서 항공편을 고르면 팀을 못 찾았고, 되묻기 목록의 첫 후보가 항공편이면 항공 팀이 항목 없이 맡아 되묻기 문장을 모델에 해석시키다 실패했다 | 고른 항목 종류에 항공 추가 · 채팅이 만든 구조화 요청은 항목 없이도 일정 관리로 |
| ④ | [decision_unit.py](../../../app/domains/travel_ops/components/conversation/decision_unit.py) | **항공만의 것** — 해석 모델에 주는 일정 목록이 항공편을 영어 종류 이름 `flight` 로 보였다(식당 · 활동 · 숙소는 한글) | 종류 이름 표에 `항공편` |

규칙 해석 경로(모델이 없거나 꺼졌을 때의 대비)의 대상 고르기도 숙소와 한 표(`_OWN_TEAM_WORDS`)로 묶었다 — 「항공 바꿔 줘」 · 「비행기 다른 걸로」라고 말하거나 화면에서 항공편을 눌러 두면 항공편이 대상이다. 번호(「2번」)는 여전히 식사 · 활동만 센다. 숙소와 항공을 함께 말하면 가리지 않는다.

**시험이 잡는지**: 고치기 전에 새 채팅 시험 5개 중 4개가 실패했다(`escalated` 등). 고침 5곳(담당 표 · 팀 선언 · 되묻기 고르기 · 구조화 요청 · 표시 이름)을 하나씩 꺼 보면 각각 시험이 실패한다(끈 뒤 복원 확인). 그 과정에서 둘째 후보 시험을 더했다 — 첫째 후보 시험만으로는 「고른 항목에서 팀 찾기」를 끄고도 통과했다.

## 시험 결과

- **mock 서버 시험(화면 반응)**: 해당 없음 — 화면 코드는 안 바꿨다.
- **이 PC 의 시험 DB 시험**(별도 DB, 가짜 환경값 · 해석 모델 · 항공 검색):
  - 구조 · 계약 · 단위(`tests/architecture` `tests/contract` `tests/unit`): 7,076 통과 · 131 건너뜀 · 실패 0.
  - e2e 전체 + 통합(`tests/integration/travel`): 1,136 통과 · 20 건너뜀 · 실패 0. ☆첫 실행은 C: 여유가 200MB 아래로 떨어져(다른 작업이 디스크를 씀) 31% 에서 실패 2건이 나와 멈추고, 이 세션이 쓰지 않는 큰 폴더(작업 폴더의 `program/`)를 지워 여유를 만든 뒤 처음부터 다시 돌렸다 — 첫 실행의 실패 2건은 어느 시험인지 기록하지 못했다(요약 없이 중단).
- **실서버 확인(x600 서버 응답)**: **안 했음.** 이유: 고친 코드가 x600 서버에 아직 없다.
- 못 돌린 시험: 파이썬 `ci-main` 전체 순서(데모 데이터 + e2e)는 하지 않았다. 통합은 `travel` 만 돌렸다(그 밖의 통합 폴더 · live · rag 는 안 돌림).

## 확인 순서 (배포 뒤, x600 서버)

1. 항공편 항목이 든 여행을 등록하거나(웹 접수에는 항공 항목을 만드는 입구가 아직 없다 — 등록 API 로만) 가진 여행에서, 채팅 「항공 다른 편으로 보여 줘」 → 「선택이 필요해요」 카드(후보 3편).
2. 고르기 → 일정 +1판 · 출발 시각이 그 편으로.
3. 웹 화면에서 이 카드가 어떻게 보이는지는 한 번도 본 적이 없다.

## 이번에 건드리지 않은 것 (남은 일)

- **웹 접수에서 항공 항목을 만드는 입구가 없다** `[10-13 반영 문서 「남은 것」]` — 항공 채팅은 등록 API 로 만든 여행에서만 쓸 수 있다.
- 「1인 ○원 이하」 · 「더 싸게」 조건이 이 길로 항공 팀 `_change` 에 전달되는지는 확인하지 못했다(`_conditions(ctx)` 가 읽는 칸이 채팅 요청에 있는지) — LB-05 와 같은 줄기라 건드리지 않았다.
- 항공 항목이 든 여행의 수정 모드(`reopen.EDITABLE_KINDS`) · 일정 조회 종류 목록(`schedule_query.KINDS` 에 항공 없음)은 확인하지 못했다.
- 기차 · 버스(팀원 브랜치)가 합쳐지면 같은 담당 표와 팀 선언이 필요하다.
