# Activity 대체 장소 연결을 문서 규칙에 맞게 고쳤다

결론: `check_feasible` 의 대체 장소 연결이 `wiki/teams/activity.md` 「Team 연결」 규칙과 어긋나 있어 코드를 문서에 맞췄고, 데이터 키·문구·시험은 팀원(kimji9663)의 `6634bf2` 구현 방식으로 맞췄다. 위급재난이면 안내하지 않고, 운영 여부를 모르는 후보는 안내문에서 뺀다. 시험은 travel·계약·DB 통합 1,324건이 통과했다(61건 건너뜀, 실패 0).

## 1. 작업 목표

- 계획: `wiki/teams/activity.md` 「구현 현황 — 작업자 B」·「Team 연결 — `read.place_candidates` 계약」.
- 어긋난 곳(RULE.md §2 0번 「작업 대상 wiki 페이지를 먼저 읽는다」를 안 지키고 구현했던 부분):
  1. 위급재난이어도 대체 장소를 추천했다 → 문서는 `withheld`(도구도 안 부름).
  2. 운영 여부를 모르는 후보를 안내문에 「미확인」으로 실었다 → 문서는 `decisions` 에만.
  3. 결과 이름이 `found`/`none`/`unknown` 이었다 → 문서는 `ranked`/`unknown`/`withheld`.
  4. 판정 3분기 `status`(problem/insufficient_info/ok)가 없었다.
  5. 선호도를 설문 `priority` 에서만 읽었다 → 문서는 `current_state["activity_preference"]` 도 읽는다.

## 2. 수행 내용

변경 파일:

- `app/modules/travel_ops/activity/team.py` — `_check_feasible` 의 모든 반환에 `status` 추가, `_recommend_alternatives` 재작성(`withheld`·`no_content_id`·`pool_unavailable`·`ranked`, 후보별 `revalidated`, `revalidation.not_checked: ["capacity"]`), `_preference` 신설(`activity_preference` 우선, 없으면 설문).
- `tests/unit/travel/test_activity_alternatives_flow.py` — 새 규칙에 맞게 고치고 7건 추가.
- `tests/unit/travel/test_activity_status_alternatives_wiring.py`(신규) — 팀원 커밋 `6634bf2` 의 `test_activity_alternatives_wiring.py` 14건을 되살렸다(9/28 `87de25f` 가 같은 파일명을 다른 내용으로 덮어써서 별도 이름). 바뀐 전제만 갱신: 재난문자 모양(`for_region`/`step`), 폴백 순서(10/1 팀 합의), `max_steps`(6→12), 도구 스텁 시험(실구현됨), 운영시간 파싱(`open_at`).
- `wiki/teams/activity.md` — 낡은 서술 정정: 폴백 순서(타입은 대분류와 한 묶음), `business_hours` 를 이제 읽음(`open_at`), 재검증 대상, 선호도 읽는 경로.

팀원 구현에서 가져온 것: `decisions.alternatives.alternatives` 키(제가 `items` 로 지었던 것을 되돌림), `revalidation.checked/not_checked`, 위급재난 안내 문장, 경고 문구(「알 수 없는 선호도 값」·「대체 장소 후보 풀을 받지 못했다」), 답변 형식(「대체 장소 후보: A(0.3km), …」).

정하지 않고 판단한 점:

- 문서의 「재검증」 표는 운영시간을 확인하지 않는다고 적었지만, 이후 `open_at` 이 들어가 후보의 운영시간을 읽는다. 그래서 `revalidated` 는 「휴무 요일이 아님」 **또는** 「그 시각 운영 중」이 확인된 경우로 넓혔고, `not_checked` 에는 정원만 남겼다. 문서에 반영했다.
- `activity_preference` 에 모르는 값이 있으면 설문으로 되돌리지 않고 경고 후 `None` 으로 처리한다(문서: 「추측하지 않는다」).

## 3. 검증

재현 (`final_project_cs/` 에서, 로컬 Docker Postgres `acop_db` 5433):

```
set PYTHONPATH=..\final_project_sample
python -m pytest tests/unit/travel tests/contract tests/integration/db -q
```

결과 원문 요약:

- travel + contract + integration/db: `1324 passed, 61 skipped, 1 warning in 19.60s`(팀원 시험 복원·키 이름 정렬 뒤. 정렬 전에는 `1310 passed`)

넓게 돌린 결과(`-k "wiki or doc or link or report"`, RAG 제외): `4 failed, 131 passed`. 실패 4건은 **변경을 stash 한 깨끗한 트리에서도 똑같이 실패**해 이번 변경과 무관하다 — `test_trip_api::test_the_plan_link_always_shows_the_latest_version`, `test_trip_intake_api::test_pdf_docx_and_xlsx_are_read_with_their_own_parsers`(`No module named 'docx'`), `test_openapi_surface::test_v1_surface_is_documented_when_it_grows`(계약 문서에 없는 `/v1/web/warmup`), `test_trip_reminders::test_a_change_notice_carries_the_plan_link`. 또 `tests/integration/rag/test_travel_corpus_retrieval.py` 는 10건이 ERROR 였다 — 새 Docker DB 에 여행 코퍼스(청크·임베딩)를 아직 적재하지 않아서로 **추정**하며 원인은 확인하지 않았다.

새 시험이 확인하는 것: 위급재난이면 `withheld` 이고 `read.place_candidates` 를 부르지 않는다 / 위급재난과 휴무 요일이 겹쳐도 `withheld` / 운영 미확인 후보는 안내문에 없고 `decisions` 에 `revalidated: False` / 미확인뿐이면 그렇게 말한다 / 「정원은 확인하지 않았습니다」 / `activity_preference` 가 설문을 이긴다 / 모르는 값은 경고 / `status` 3분기.

기존 `test_activity_alternatives_wiring.py` 의 `test_disrupted_does_not_call_place_candidates` 는 수정 없이 계속 통과한다(같은 규칙).
